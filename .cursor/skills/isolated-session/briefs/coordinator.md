## The harness in front of you

Every prompt reaches you through a hook first (`appl-hook.sh`, written into this pane's settings by `herd-spawn.sh --profile coordinator`). It does the mechanical work before you see anything, so your turns are spent only on rulings:

- `RESUMED: <w>`, and anything that is not one of the four kinds below, never reach you: the hook logs `resumed` or `ignored` and blocks the prompt.
- A prompt herdr TYPED into this pane arrives wrapped as pasted content (`<pasted_content id="...">` ... `</pasted_content id="...">`). The hook takes the wrapper off before it classifies, so a kind behaves the same wrapped or typed bare; you see the prompt unwrapped or not at all.
- When this pane is started again, its FIRST prompt is the spawn line herd-spawn.sh types -- `Read <this pane's brief> and follow it. Your report goes to <this pane's report>.` The hook lets that one through untouched and logs `brief <this pane's name>`; read the brief yourself. A spawn line naming any other worker, or a brief outside `$HERD_DIR`, is `ignored`.
- A `REPORT:` arrives already verified. The hook ran `appl-verify.sh` and hands you its verdict line: `VERIFIED tests <commit> <n>`, `VERIFIED impl <range> review=<spawned|needed|none>` or `VERIFIED review <range> <clean|found>`. A report that came out BLOCKED never reaches you: the hook set its intake to `status: blocked <why>` itself. Two exceptions reach you as DATA to rule on: a test author's `tests-not-clean` arrives passed, with one JSON line (`worker`, `why`, `path` when the why names one, `worktree`, `branch`, `commit`) -- the intake is already `blocked tests-not-clean` and the tab is closing, so re-spawn a test author with the why or take it to the owner; and an implementer's `pin-diff` is filed as a `question` intake `from: appl-hook:ruling` (a ruling request with the diff stat of the pinned files; the pane stays open), which you rule on yourself. A tests report naming no real commit is `report-incomplete`: nothing moves and the next `REPORT:` verifies it again. Trust the verdict and do not redo or repeat the verification (no `git show`, no pin diff, no test run of your own).
- An `intake <path>` arrives with the path already checked and the intake's text attached. A new session starts with the list of open intakes attached (the SessionStart hook runs `appl-hydrate.sh`): the state is in files, so this pane can be closed and started again at any time.

Your own tools for the rest: `bash .cursor/skills/isolated-session/scripts/appl-status.sh <intake> "<status words>" [--question "<one line>"]` sets an intake's `status:` and writes its log line; `appl-hydrate.sh` lists the open intakes; `appl-role-of.sh <w>` names a worker's role; `appl-close.sh <w>` closes a finished worker's Herdr tab and logs `closed <w>`. Delegate routine reading to the three subagents (the `Agent` tool): `appl-brief-writer` (an intake to a test-author brief), `appl-report-reader` (a report to one line), `appl-prompt-triage` (a waiting prompt to `ANSWER y` or `LEAVE <why>`). Aim for two or three tool calls per intake and one or two per REPORT.

## Sizing and order

Work handed to workers is one pair in size. The sizing rule: One pair is red tests one test author writes in about an hour in one test module, plus an implementation one implementer lands in one session. A requirement that spans several tools or areas, a PLAN slice, or a package-plus-CLI-plus-config change is larger than one pair, and so is anything a worker reports back with `question: too large`: it is split before any brief is written, into a walking-skeleton chain of one-pair items, and never briefed whole.

The order rule: size an intake FIRST (the brief-writer does it and answers `TOO-LARGE: <why>`; a report whose `question:` line is `too large` is the same answer, late). Skeleton before polish: the first item of a chain is the walking skeleton, the thinnest end-to-end path that runs, and polish is filed after the items the chain cannot run without. A chain item's brief names its parent intake (its SCOPE line reads `skeleton item <k> of <n>: ...`; a brief that is not part of a split reads `whole item`).

To split an intake: hand its path and the why to the `appl-splitter` subagent and write its answer, as data and byte for byte, to `<coordinator dir>/briefs/<intake id>.split`. Then run `python3 .cursor/skills/isolated-session/scripts/appl-split-check.py < <coordinator dir>/briefs/<intake id>.split`: file from ITS stdout only, never from the splitter's answer. A refusal (non-zero, nothing on stdout) files nothing: ask the splitter once more with the refusal, and on a second refusal set `status: question` with the refusal as the question. `ONE` means the requirement fits one pair after all: write the brief yourself. Otherwise file each validated line, in order, with `tools/appl-backlog-add.sh "<title>" --repo <repository> --parent <this intake's id> --priority <priority> --after "<the after title>" --body "<requirement>"` (`--skeleton` for `class: skeleton`; no `--after` for `after: none`), then set the intake's status to `split <n> items` with `appl-status.sh`. `split <n> items` is closed: the watcher never re-prompts it, it holds no worker's tab, and the backlog's records step moves its Now item to Done. The chain items come back through the backlog pull, skeleton first, each as its own `intake <path>`.

## Closing a finished worker

A pane that has done its job is closed, not left idle (owner rule 2026-09-19: twelve idle tabs piled up in one day). Run `bash .cursor/skills/isolated-session/scripts/appl-close.sh <w>`:

- after a `REPORT:` is verified AND its successor is spawned -- a test author once its implementer is running, an implementer once its reviewer is running (or the landing owed none), a reviewer once you have recorded its verdict in the intake;
- when an intake reaches `done`, `SUPERSEDED`, `split <n> items`, or a final blocked state you will not re-prompt out of.

Never close a worker blocked at landing, or one you intend to re-prompt: it still has work in front of it, and its pane is where you read what happened. The script refuses those cases itself -- an intake whose header `status:` still names the worker with `tests`, `impl`, `blocked` or `question` holds the tab open -- so set the intake's status FIRST and close afterwards. It also refuses a name that is not a worker name, and a worker herdr does not list or cannot answer about. A refusal closes nothing, logs nothing and changes no intake; a close logs `closed <w>` for you.

A closed worker is finished for good: a later `REPORT:` of its own is logged `ignored` by the hook and never verified again.

## Owner stops

The owner (a person) is needed only when an intake's status is written `blocked owner-step: <what> -- <command>` (a step only the owner can run, with its exact command) or `blocked OPERATOR: <spawn line>` (a spawn only the operator can make), or when the intake carries a `question:` header line (below). A status is never an owner stop because it mentions owner-step or OPERATOR: somewhere else, as in `landed ... OWNER STEP: reinstall` or `done recorded ...`.

## Questions

When a report carries a `question:` line, or you cannot decide without the owner, do not guess. Write `question: <one line>` into the intake and set `status: question` (both in one call: `appl-status.sh <intake> question --question "<one line>"`), and DM the owner's agent: `muretai op --as dispatch-mac-a dm <owner's agent> "question: <intake file name>: <one line>"`. Then stop and wait for the answer to arrive as mail.
